Why TypeScript, not JSON or markdown

Policies are domain data, not loose documents — they have a fixed shape (id, title, effective, owner, sections) we want type-checked. TS means IDE jump-to-definition, no schema drift, single source of truth that compiles or doesn't. JSON would lose the types; markdown would require a parser and a section-id scheme that lives outside the data.

src/lib/knowledge/policies.ts

Why one chunk per section

Each policy section already is the natural atomic unit (POL-01 §1.4 = "Accounts are locked after 5 attempts..."). Sub- chunking would dilute citations — the agent needs to point at a section, not a sentence. 60 sections × 1536 dims sits trivially in memory; Qdrant's HNSW doesn't even build an index at this size.

allChunks() in policies.ts

Stable point IDs

pointId = policyNum * 10000 + major * 100 + minor. POL-01 §1.4 → 10104. Deterministic and collision-free for our numbering scheme. Re-running npm run ingest upserts over the same ids — no duplicates, no drift, no migration script.

Embedding input

We embed ${'${policyId} ${title} §${sectionId}\\n${text}'} — not just the section body. The title in the embedding string boosts retrieval for terse queries ("VPN policy?") that don't quote the section text verbatim. Empirically improves recall on the short-question end of the eval set.

Run via:

npm run ingest             # incremental upsert
npm run ingest -- --reset  # drop & recreate the collection

Why a custom client (not @atlaskit/jira-client or similar)

The official Node clients are heavy, opinionated, and drag in types for every JIRA feature we don't use. We need ~10 endpoints. A thin JiraClient wrapping fetch with auth + JSON serialization is ~80 lines, fully typed against only the fields we read, and lets us own the error surface (JiraApiError with the actual response body).

src/lib/jira/client.ts · src/lib/jira/tickets.ts

ADF (Atlassian Document Format) — both directions

JIRA Cloud v3 returns descriptions as ADF (nested JSON, not plain text) and accepts comments as ADF. We have adfToPlainText() for inbound (so the agent sees a flat string) and markdownToAdf() for outbound (so the agent's formatComment() markdown renders with the right styling in JIRA).

src/lib/jira/tickets.ts · src/lib/jira/comments.ts

Auth

Basic auth: Atlassian account email + API token (created at id.atlassian.com). Stored in env vars only, never committed. The client accepts OAuth bearer too if you want to swap later — both are typed in JiraAuth.

Queue semantics

The "queue" is whatever JQL you set in JIRA_QUEUE_JQL — typically status = Backlog AND labels = "seeded". The /tickets page and the load-tickets batch both read from it. Triage moves tickets out of the queue via the transition IDs, so the queue naturally drains as the agent works.

3. Eval & calibration

The 50-ticket benchmark plus the sweep harness is what turns "the agent feels good" into "the agent scores 50/50 with RETRIEVAL_SCORE_THRESHOLD=0.30, documented."

The eval harness scores every ticket into one of six buckets — see the triage pipeline doc for the bucket weights and the post-validation guards that produce them. The sweep wraps it: runs the eval N times across a threshold range, picks the value with the lowest weighted error, writes the full per-ticket data to reports/sweeps/<id>.json so a future operator can answer "at threshold=0.45, which specific tickets newly failed compared to 0.40?" without re-running.

What the sweep is actually varying

The "threshold" the sweep tunes is RETRIEVAL_SCORE_THRESHOLD — but it's not a retrieval filter. Every cosine top-K hit goes into the LLM context regardless of score. The threshold is the floor used by Guard 2 in the triage pipeline: after the LLM proposes a RESOLVE, the post-validation step compares the top retrieval hit's cosine similarity (ticket embedding vs the top-matching policy section's embedding) to the threshold. If it's below, the RESOLVE is downgraded to DEFER · LOW_CONFIDENCE.

So the sweep is searching for the precision/recall trade-off on a single deterministic guard, not on retrieval itself:

  • Too low → confident-but-wrong RESOLVEs slip through (false_resolve, weighted 3×).
  • Too high → correct RESOLVEs get over-deferred (missed_resolve, weighted 1×).
  • The 3× asymmetry tells the optimizer which way to err. At our corpus, the sweet spot landed at 0.30.
See triage pipeline → Guard 2 for the exact line where the comparison happens.

4. Persistence layers

Layer What's in it Survives Next dev restart? Survives Docker restart?
Qdrant volume 60 policy-section embeddings + payload ✓ ✓ (Docker volume)
JIRA Cloud Authoritative tickets, comments, labels, assignees ✓ ✓ (external)
reports/sweeps/ Full per-ticket eval data per sweep run ✓ ✓ (filesystem)
reports/eval.csv Rubric-required deliverable when CLI passes --out ✓ ✓
triage-store (globalThis Map) Recent triage decisions for the dashboard list ✗ (in-memory) n/a
eval-store (globalThis cache) Last completed eval run, for /eval hydration ✗ (in-memory) n/a

The in-memory stores are bound to globalThis so they survive Next's bundler creating multiple module instances within a single process. They're intentionally ephemeral: JIRA is the authoritative record for triage decisions (via the comment we posted); the in-memory store is a dashboard convenience.

5. Deployment shape

Local dev (what's running right now)

  • docker compose up qdrant — vector store, one container
  • npm run dev — Next.js on the host, port 3001
  • All external APIs (Anthropic / OpenAI / Cohere / JIRA) hit over the network
  • State: Qdrant volume on disk + reports/ in repo + in-memory caches

Production shape (what would change)

  • Containerize Next.js (Vercel or a managed Node host)
  • Qdrant on managed cloud OR same Docker volume on a persistent disk
  • Move in-memory stores to Redis or a real DB (Postgres) so they survive restarts and scale horizontally
  • JIRA webhook → /api/jira/webhook instead of polling — already wired
  • Structured logging with request IDs; alerts on trace.downgraded rate
  • LLM provider failover (Anthropic primary → OpenAI fallback)
